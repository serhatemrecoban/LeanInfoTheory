# LeanInfoTheory `v0.1.x` public API contract

This document freezes the project-owned public surface selected for the
LeanInfoTheory `v0.1.x` release line. It complements the mathematical scope and
release policy in [`v0.1-release-contract.md`](v0.1-release-contract.md). The
machine-readable inventory is
[`v0.1-public-api.json`](v0.1-public-api.json); regenerate or verify it with:

```powershell
python scripts/generate_v0_1_public_api.py
python scripts/generate_v0_1_public_api.py --check
```

The manifest is source-derived and records supported module paths,
project-owned declaration names and kinds, reviewed `simp` attributes, and the
lightweight-root export façade. It is an exact compatibility baseline, but it
does not contain type/signature fingerprints. The separate
[signature-bearing API documentation](api-documentation.md) renders and checks
the current elaborated declarations. Together these artifacts document the
selected surface; neither generated HTML nor the manifest replaces the stated
source-compatibility policy and review of signature changes.

## Stability promise

The following are supported throughout `0.1.x`:

- the module paths in the supported-module list below;
- the project-owned public declarations in those modules, including their
  names, namespaces, types, assumptions, and documented semantics;
- the 92 explicit convenience exports from
  `LeanInfoTheory.InformationMeasures` into `LeanInfoTheory`;
- the reviewed public attributes recorded in the manifest; and
- the lightweight and full-umbrella import boundaries described below.

Patch releases may add declarations or compatibility aliases. They will not
remove or silently change the meaning of this frozen surface. A necessary
breaking change must be documented and deferred to a later minor release such
as `0.2.0`.

Private declarations, proof terms, implementation structure, generated names
not listed in the manifest, imported mathlib declarations, and modules marked
non-stable below are not covered by this source-compatibility promise.

All 601 have source documentation. Of these, 557 use the canonical

## Signature-bearing generated documentation

The isolated, pinned doc-gen4 gate has locally produced and validated 31
supported module pages containing all 601 project-owned declarations exactly
once, with rendered declaration headers and nonempty types. It also resolves
the 92 lightweight-root exports to their canonical documented targets and
excludes all 13 non-stable modules. Run the explicit milestone gate from the
repository root with:

```powershell
python scripts/validate_release.py api-docs
```

Lean `export` commands create no additional environment constants, so the 92
convenience exports do not have duplicate declaration blocks. Their manifest
table plus the canonical declaration pages document that façade. The current
generated tree uses local `file:` source links and is intentionally unpublished;
website staging is separate release work. See
[`api-documentation.md`](api-documentation.md) for the source-link, equation,
build-isolation, and validation contract.

These rendered types are evidence for the current tree, not committed signature
fingerprints. Until such fingerprints are deliberately added to the versioned
manifest, every same-name type or assumption change still requires explicit API
review rather than relying on the manifest generator to detect it automatically.

The public naming policy is compatibility-first:

- PMF-facing and random-variable-facing declarations preserve the established
  `...`/`...Of` distinction;
- descriptive existing names remain stable, including names that expose an
  orientation needed to disambiguate symmetric statements;
- the previously reviewed textbook-facing compatibility aliases remain
  available;
- speculative shorter aliases are not added without demonstrated consumer or
  theorem-search pressure; and
- entropy, MI, CMI, chain-rule, equality-characterization, and semantic-view
  rewrites remain explicit unless they have a reviewed, terminating,
  construction-reducing `simp` orientation.

## Mathematical conventions carried by the API

- Canonical real-valued information quantities are measured in nats and
  interoperate directly with mathlib's natural-logarithm entropy and KL APIs.
  `LeanInfoTheory.Shannon.Units` adds the opt-in scalar conversions
  `natsToBase` and `natsToBits`; it does not define a parallel bit-valued
  theorem hierarchy.
- Finite-alphabet assumptions remain explicit in each declaration. Source
  probability spaces are not made finite merely because a random variable has
  a finite codomain.
- Two reviewed stronger contracts are intentionally frozen rather than weakened
  speculatively: `channelPosterior` uses `[Fintype alpha]`, and
  `isSufficientStatistic_iff_exists_fisherNeymanFactorization` uses
  `[Finite alpha] [Nonempty alpha]`. Revisit them only with concrete consumer
  pressure and compatibility-preserving wrappers where possible.
- Support-sensitive statements retain their documented support hypotheses.
  Conditional laws retain the project's null-fiber conventions.
- Canonical KL results use `ENNReal`; real-valued KL consequences retain the
  required finiteness or absolute-continuity guards so that `ENNReal.top` is
  not silently converted to zero.
- Sufficiency, recovery, Markov, conditional-independence, finite-family, and
  convexity declarations remain in their current focused owners. No module is
  split or declaration moved solely because an implementation file is large.

No example declaration is promoted into the stable API for `v0.1.0`. The
examples remain maintained build consumers, but their declaration names and
internal fixtures may evolve without a `0.2.0` compatibility event.

Certificate parsers, checked-certificate data structures, primitive-certificate
machinery, and certificate demos are not part of LeanInfoTheory's `v0.1.x`
surface. General finite-family and Shannon inequalities formerly consumed by
certificates remain supported mathematical API. Downstream certificate
applications and paper-specific constructions belong in separate projects.

## Changing the manifest

Any proposed edit to a supported module must compare the regenerated manifest
with the checked-in baseline. Additive API growth still requires the ordinary
naming, assumption, namespace, ownership, documentation, and focused-consumer
review. A removal, rename, signature change, attribute change, module move, or
import-boundary change requires a plan-health review and must not be presented
as a compatible `0.1.x` patch without an explicit migration decision.
