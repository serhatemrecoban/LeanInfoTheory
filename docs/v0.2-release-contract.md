All states preserve Apache-2.0, EPFL rights-holder, sole creator Serhat Emre
Coban and the MIL affiliation. Historical references retain their issued
identifiers. A candidate does not reuse the first release's date or version DOI.
The internal docbuild package and all toolchain/dependency pins remain unchanged.
Unknown states, versions, routes and JSON fields are rejected.

The historical configuration comparison remains byte-exact after its existing
uniform LF/CRLF treatment. Only an explicit `candidate` state permits the exact
root Lake line `version = "0.2.0"` to project back to `version = "0.1.0"`.
Every other byte must still match the original configuration hashes. Extra Lean
options, changed pins, other versions and alternate Lake configuration are not
permitted by this projection.

including the post-v0.1.0 additions. A minor version grants no automatic right to
break retained names, assumptions, types, semantics, owners, imports or reviewed
attributes. No breaking mathematical/API migration is selected.

umbrella simp membership. Source inventory and rendered HTML cannot replace it.

The canonical [candidate contract](compatibility/v0.2.0-candidate-contract.json)
and [digest approval](compatibility/v0.2.0-candidate-approval.json) now retain the
actual clean checkpoint 05f9bec capture following independent artifact examination. Lifecycle

external-consumer and formal C24.07 gates. Steps 4–5 intentionally had no canonical

Capture writes a new ignored file exclusively and never writes approval. Dirty
or isolated experimental captures cannot establish the canonical baseline.
The separate approval envelope binds the exact artifact digest, full inventory,
producer identity and clean export checkpoint to explicit source-bound review.
A changed artifact invalidates that approval; regeneration supplies no authority.
Normal checks use only the canonical paths, without a baseline override switch.

Producer fingerprints bind actual mathematical/configuration/exporter/checker
inputs and clean installed dependency identities. They exclude the artifact,
approval output and containing commit, avoiding recursive capture. Lifecycle
phase/retention/digest are preserved as observations; the compared release
projection binds target, actual package, routes and publication prohibition.
The state checker itself is fingerprinted. Full validation identities separately
include raw state and the new checker/artifact/approval inputs when present.
The actual export-source checkpoint is distinct from the later commit containing
the reviewed artifact. Exact final qualified commit/tree identities belong in
separate completion evidence.

The negative fixture must compile and export an actual post-v0.1.0 signature
change with the same declaration name, owner and count, then obtain a qualified-
name, structural-path rejection. Compiler failure, inventory staleness or producer
fingerprint drift alone receives no credit for that requirement. An unchanged
positive control and unchanged historical 601 types are checked separately.
Experimental fixtures do not qualify a release baseline.


The complete compiler version string retains its platform target as provenance.
Compatibility compares strictly parsed Lean version, full pinned commit and build
mode, allowing a target-triple difference alone. Windows/Linux/Apple target
comparisons have synthetic controls; actual platform qualification remains a
separate execution. Type, source-file, dependency and reviewed-boundary comparisons
keep their existing guards.

## Separate routes and artifacts

All routes are below the existing `/LeanInfoTheory/` project subpath.

| Route | Contract |
| --- | --- |
| `/docs/` | Documentation landing; stable continues to select released `v0.1.0`. |
| `/docs/v0.1.0/` | Immutable historical API, exact release checkout, tag, source identity and route digest. |
| `/docs/current/` | Explicit development/candidate API with its own current source/configuration/dependencies/manifest/link-mode identity. |
| `/docs/v0.2.0/` | Reserved for a later immutable approved release; any local placeholder must say reserved and unpublished. |

Candidate composition is always `publishable=false` and marked
`NOT_FOR_PUBLICATION`. The current API keeps its own checked two-pass/content
attestation. Separate current and frozen route digests prevent swapping them.
Staging and checking both require the explicit expected source commit and frozen
source/site roots; rehashing a tampered artifact's own metadata is insufficient.
Those local machine paths are not serialized into the staged artifact.

Local candidate mode accepts an exact clean checkout, including detached HEAD,
without invented GitHub Actions variables. It cannot authorize deployment.
File-mode source anchors are sanitized for preview; unsupported mutable source
links are disabled rather than promoted to immutable links. GitHub source mode
must match the exact expected commit. No local result asserts remote availability
of an unpublished SHA. Dependency-link advisories are checked separately for each
route under explicit bounded policies, never a combined count that hides drift.

The frozen v0.1.0 staging branch and its historical attestation contract remain
unchanged. Candidate/current output, stale bodies/docstrings, wrong versions or
commits, swapped attestations and changed historical bytes are rejected. Machine-
local links cannot enter publishable output. Existing Pages defaults stay
`publish=false`; no automatic tag/release workflow is added and no stable pointer
is switched. Actual expensive current API/artifact qualification belongs to
C24.08, not to synthetic routing tests or fixture commits.

The [content-proposal history and current boundary](qualification/c24-candidate-content-proposal.md)

history. A containing successor requires its own exact Git approval. Clean
candidate/staging guards inspect the Git tree without reading or deleting the
local file. The original C24.04 preparation changed no index, HEAD or local bytes.

candidate. Documentation-generation or source-link changes require renewed API/
artifact qualification; mathematical/API changes additionally require affected
consumers and renewed review. Publication must name the actual final qualified
