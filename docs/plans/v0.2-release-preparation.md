## Website size: findings and approved hosting design

The C24 composed preview is 1,316,901,746 bytes. The current raw API artifact is
664,519,346 bytes, with 5,554 files. LeanInfoTheory's own module directory accounts
for about 3 MB; most space belongs to the imported Lean/mathlib/dependency closure
and generated indexes. Two complete version trees exceed the
[GitHub Pages 1 GB published-site limit](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
Compression of a deployment archive does not reduce the published tree's size.

The pinned doc-gen4 implementation ties search, instance lists, reverse-import
links and module navigation to each tree's declaration data and relative root.
Removing duplicated dependency HTML alone would break links. Sharing it safely
would require deliberate routing/index work and checks for version-context
mixing. A later Lean/mathlib upgrade can require a different dependency tree.
No complete byte-identity/deduplication saving is claimed: the long comparison
scan was interrupted after the size and dependency structure were established.

**Selected design:** retain the main website at
`https://serhatemrecoban.github.io/LeanInfoTheory/`, including its frozen
`/docs/v0.1.0/` documentation. Update its current pages with the completed C9-C24
programme, v0.2.0 release information, installation guidance and approved PFR
case-study insights. Put the complete v0.2.0 API snapshot, including dependency
pages and search data, on a separate public GitHub Pages project site. Use the
provided `github.io` address; no paid host or purchased domain is selected.
The approved repository is `serhatemrecoban/LeanInfoTheory-API`. Its reusable
entry point is `https://serhatemrecoban.github.io/LeanInfoTheory-API/`; this release
uses the complete versioned snapshot at `/LeanInfoTheory-API/v0.2.0/`. The
repository has not been created. The 1 GB guard applies to the entire deployed
API site, not separately to its version folders. Later snapshots that do not fit
can live on separate sites linked from this permanent entry point, preserving
existing snapshot URLs and avoiding duplicate dependency trees.

A fresh read-only inventory of the existing C24 staged artifact measured
655,321,297 bytes in `docs/current/` and 661,580,449 bytes in the rest of the
site, including frozen v0.1.0. Thus both proposed sites fit below 1 GB with about
one-third capacity remaining. These are measured inputs to the split, not final
publishable artifacts: GitHub-mode source links, cross-site return navigation,
small entry pages and metadata must still be prepared and checked. The split
resolves the present aggregate-size design blocker; it does not complete release
or production-host qualification.

Keep the main documentation entry points and version selector small, linking to
the appropriate API site without duplicating the complete new API tree on the
main site. Record the revised routing contract explicitly in Step 2. A future
release may use its own API project site, each subject to its own 1 GB limit;
adding release numbers does not itself accumulate all snapshots on one site.

Archive complete portable versioned API packages and keep deployment settings
separate from generation. If one future snapshot exceeds the per-site limit,
reassess dependency splitting or larger hosting then. R2 is a possible later
migration destination, not the current choice; older API sites can remain in
place so existing links keep working. The earlier R2/custom-domain recommendation
is superseded. Small costs are acceptable in principle, but no particular expense,
subscription, domain, account, bucket or billing action is authorized.

This design preserves full signatures, documentation and dependency navigation
without trimming mathematical coverage. It adds a documentation repository and
deployment to maintain. Quality acceptance must
cover search, declaration anchors, imported-by/instance links, project-subpath
navigation, directory/index and repeated-slash handling, correct content types
for generated data, mobile rendering, and exact public-SHA source links on the
intended host. Keep each API tree and its data on one origin where possible.

For later releases, retain each self-contained immutable snapshot and update the
small version index/stable pointer after approval. Recheck each individual site's
size, host limits, routes and version identity at each release gate. There is no
claim that a future single snapshot can never exceed 1 GB. No automatic progress
monitoring is selected.

An alternative single-site layout could deduplicate matching dependencies for v0.2.0, but
requires more custom navigation/search logic and renewed capacity analysis when
dependency pins change. It is not a durable guarantee for the third release.
No layout may raise the existing guard silently or replace historical
documentation bytes without reconciling their deployed provenance.
